# Service Worker 配置文件 {#service-worker-configuration-file}

本主题介绍 Service Worker 配置文件中的各项属性。

## 修改配置 {#modifying-the-configuration}

`ngsw-config.json` 这个 JSON 配置文件指定了 Angular Service Worker 应该缓存（cache）哪些文件和数据 URL，以及应该如何更新已缓存的文件和数据。
[Angular CLI](/tools/cli) 会在 `ng build` 期间处理这个配置文件。

所有文件路径都必须以 `/` 开头，它对应部署目录 —— 在 CLI 项目中通常是 `dist/<project-name>`。

除非另有说明，模式都使用一种**受限的\*** glob 格式，它在内部会被转换为正则表达式：

| Glob 格式 | 详情                                                                                                   |
| :----------- | :----------------------------------------------------------------------------------------------------- |
| `**`         | 匹配 0 个或多个路径段                                                                        |
| `*`          | 匹配 0 个或多个除 `/` 之外的字符                                                             |
| `?`          | 恰好匹配一个除 `/` 之外的字符                                                            |
| `!` 前缀   | 把该模式标记为否定模式，即只包含不匹配该模式的文件 |

::: warning 特殊字符需要转义
请注意，在内部把 glob 转换为正则表达式时，某些在正则表达式中具有特殊含义的字符不会被转义，模式也不会被包裹在 `^`/`$` 中。

`$` 在正则表达式中是一个特殊字符，用于匹配字符串结尾；把 glob 模式转换为正则表达式时，它不会被自动转义。

如果想按字面匹配 `$` 字符，就必须自己转义它（使用 `\\$`）。例如，glob 模式 `/foo/bar/$value` 会生成一个永远无法匹配的表达式，因为字符串在结束之后不可能还有任何字符。

把模式转换为正则表达式时，不会自动用 `^` 和 `$` 包裹它。因此，这些模式会部分匹配请求的 URL。

如果希望模式匹配 URL 的开头和/或结尾，可以自己加上 `^`/`$`。例如，glob 模式 `/foo/bar/*.js` 会同时匹配 `.js` 和 `.json` 文件。如果只想匹配 `.js` 文件，请使用 `/foo/bar/*.js$`。
:::

模式示例：

| 模式     | 详情                               |
| :----------- | :------------------------------------ |
| `/**/*.html` | 指定所有 HTML 文件              |
| `/*.html`    | 只指定根目录下的 HTML 文件 |
| `!/**/*.map` | 排除所有源码映射（source map）                |

## Service Worker 配置属性 {#service-worker-configuration-properties}

以下各节介绍配置文件中的每个属性。

### `appData` {#appdata}

在这一节中，你可以传入任何想要的数据，用来描述应用的这个特定版本。
`SwUpdate` 服务会把这些数据包含在更新通知中。
许多应用会用这一节提供额外信息，以便显示 UI 弹窗，通知用户有可用的更新。

### `index` {#index}

指定用作索引页的文件，用来响应导航请求（navigation request）。
通常是 `/index.html`。

### `assetGroups` {#assetgroups}

**资源**（Asset）是应用版本的一部分，会随应用一起更新。
它们既可以包括从页面所在源加载的资源，也可以包括从 CDN 和其他外部 URL 加载的第三方资源。
由于并非所有这类外部 URL 都能在构建时确定，因此也可以匹配 URL 模式。

::: tip 提示
为了让 Service Worker 能处理从不同源加载的资源，请确保每个源的服务器都正确配置了 [CORS](https://developer.mozilla.org/docs/Web/HTTP/CORS)。

:::

该字段包含一个资源组数组，每个资源组都定义了一组资源以及缓存它们所用的策略。

```ts
{
  "assetGroups": [
    {
      …
    },
    {
      …
    }
  ]
}
```

::: tip 提示
当 ServiceWorker 处理请求时，它会按照资源组在 `ngsw-config.json` 中出现的顺序依次检查。
第一个与所请求资源匹配的资源组将处理该请求。

:::

建议把更具体的资源组放在列表中更靠前的位置。
例如，匹配 `/foo.js` 的资源组应该出现在匹配 `*.js` 的资源组之前。

每个资源组既指定了一组资源，也指定了管理这些资源的策略。
该策略决定了何时获取这些资源，以及检测到变化时会发生什么。

资源组遵循如下 TypeScript 接口：

```ts
interface AssetGroup {
  name: string;
  installMode?: 'prefetch' | 'lazy';
  updateMode?: 'prefetch' | 'lazy';
  resources: {
    files?: string[];
    urls?: string[];
  };
  cacheQueryOptions?: {
    ignoreSearch?: boolean;
  };
}
```

每个 `AssetGroup` 都由以下资源组属性定义。

#### `name` {#name}

`name` 是必填项。
它用于在不同版本的配置之间标识这个特定的资源组。

#### `installMode` {#installmode}

`installMode` 决定了这些资源最初如何被缓存。
`installMode` 可以是以下两个值之一：

| 值     | 详情                                                                                                                                                                                                                                                                                                                                                                                       |
| :--------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prefetch` | 告诉 Angular Service Worker 在缓存应用的当前版本时，获取列出的每一个资源。这会占用较多带宽，但能确保无论何时请求这些资源，它们都可用，即使浏览器当前处于离线状态。                                                                                                                       |
| `lazy`     | 不预先缓存任何资源。Angular Service Worker 只会缓存它收到请求的那些资源。这是一种按需缓存模式。从未被请求过的资源不会被缓存。这对于不同分辨率的图片之类的资源很有用，这样 Service Worker 只会缓存适合特定屏幕尺寸和方向的资源。 |

默认为 `prefetch`。

#### `updateMode` {#updatemode}

对于已经在缓存中的资源，`updateMode` 决定了发现应用的新版本时的缓存行为。
组中自上一版本以来发生了变化的任何资源，都会按照 `updateMode` 进行更新。

| 值     | 详情                                                                                                                                                                                                                                  |
| :--------- | :--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `prefetch` | 告诉 Service Worker 立即下载并缓存发生变化的资源。                                                                                                                                                        |
| `lazy`     | 告诉 Service Worker 不要缓存这些资源，而是把它们视为未请求过的资源，等到再次被请求时才更新它们。只有当 `installMode` 也是 `lazy` 时，`updateMode` 为 `lazy` 才有效。 |

默认值与 `installMode` 的设置值相同。

#### `resources` {#resources}

这一节描述要缓存的资源，分为以下几组：

| 资源分组 | 详情                                                                                                                                                                                                                                                                                                                                                                                                       |
| :-------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `files`         | 列出与分发目录中的文件相匹配的模式。它们可以是单个文件，也可以是匹配多个文件的类 glob 模式。                                                                                                                                                                                                                                                                  |
| `urls`          | 包括在运行时进行匹配的 URL 和 URL 模式。这些资源不会被直接获取，也没有内容哈希（hash），但会根据它们的 HTTP 头进行缓存。这对于 Google Fonts 服务之类的 CDN 最有用。 <br /> _（不支持否定 glob 模式，`?` 会按字面匹配；也就是说，它只匹配 `?` 字符本身。）_ |

#### `cacheQueryOptions` {#cachequeryoptions}

这些选项用于修改请求的匹配行为。
它们会被传给浏览器的 `Cache#match` 函数。
详情参见 [MDN](https://developer.mozilla.org/docs/Web/API/Cache/match)。
目前只支持以下选项：

| 选项        | 详情                                       |
| :------------- | :-------------------------------------------- |
| `ignoreSearch` | 忽略查询参数。默认为 `false`。 |

### `dataGroups` {#datagroups}

与资源不同，数据请求不会随应用一起进行版本管理。
它们会根据手动配置的策略进行缓存，这些策略更适用于 API 请求和其他数据依赖之类的场景。

该字段包含一个数据组（data group）数组，每个数据组都定义了一组数据资源以及缓存它们所用的策略。

```json
{
  "dataGroups": [
    {
      …
    },
    {
      …
    }
  ]
}
```

::: tip 提示
当 ServiceWorker 处理请求时，它会按照数据组在 `ngsw-config.json` 中出现的顺序依次检查。
第一个与所请求资源匹配的数据组将处理该请求。

:::

建议把更具体的数据组放在列表中更靠前的位置。
例如，匹配 `/api/foo.json` 的数据组应该出现在匹配 `/api/*.json` 的数据组之前。

数据组遵循如下 TypeScript 接口：

```ts
export interface DataGroup {
  name: string;
  urls: string[];
  version?: number;
  cacheConfig: {
    maxSize: number;
    maxAge: string;
    timeout?: string;
    refreshAhead?: string;
    strategy?: 'freshness' | 'performance';
  };
  cacheQueryOptions?: {
    ignoreSearch?: boolean;
  };
}
```

每个 `DataGroup` 都由以下数据组属性定义。

#### `name` {#datagroups-name}

与 `assetGroups` 类似，每个数据组都有一个 `name` 来唯一标识它。

#### `urls` {#urls}

URL 模式列表。
与这些模式相匹配的 URL 会按照该数据组的策略进行缓存。
只有不会修改数据的请求（GET 和 HEAD）才会被缓存。

- 不支持否定 glob 模式
- `?` 按字面匹配；也就是说，它**只**匹配 `?` 字符

#### `version` {#version}

API 有时会以不向后兼容的方式更改格式。
应用的新版本可能与旧的 API 格式不兼容，因此也可能与该 API 现有的已缓存资源不兼容。

`version` 提供了一种机制，用于表明正在缓存的资源已经以不向后兼容的方式进行了更新，旧的缓存条目 —— 即来自之前版本的条目 —— 应该被丢弃。

`version` 是一个整数字段，默认为 `1`。

#### `cacheConfig` {#cacheconfig}

以下属性定义了缓存匹配请求时所用的策略。

##### `maxSize` {#maxsize}

缓存中条目（即响应）的最大数量。

::: danger 严重
不设上限的缓存可能会无限增长，最终超出存储配额，导致被清除。

:::

##### `maxAge` {#maxage}

`maxAge` 参数表示响应在被视为无效并被清除之前，可以在缓存中保留多长时间。`maxAge` 是一个时长字符串，使用以下单位后缀：

| 后缀 | 详情      |
| :------- | :----------- |
| `d`      | 天         |
| `h`      | 小时        |
| `m`      | 分钟      |
| `s`      | 秒      |
| `u`      | 毫秒 |

例如，字符串 `3d12h` 表示内容最多缓存三天半。

##### `timeout` {#timeout}

这个时长字符串指定网络超时时间。
网络超时是指 Angular Service Worker 在使用缓存的响应之前（如果配置为这样做）等待网络响应的时长。
`timeout` 是一个时长字符串，使用以下单位后缀：

| 后缀 | 详情      |
| :------- | :----------- |
| `d`      | 天         |
| `h`      | 小时        |
| `m`      | 分钟      |
| `s`      | 秒      |
| `u`      | 毫秒 |

例如，字符串 `5s30u` 表示 5 秒 30 毫秒的网络超时。

##### `refreshAhead` {#refreshahead}

这个时长字符串指定在已缓存资源过期之前多长时间，Angular Service Worker 应该主动尝试从网络刷新该资源。
`refreshAhead` 时长是一个可选配置，它决定了 Service Worker 应在已缓存响应过期之前多久发起请求，从网络刷新该资源。

| 后缀 | 详情      |
| :------- | :----------- |
| `d`      | 天         |
| `h`      | 小时        |
| `m`      | 分钟      |
| `s`      | 秒      |
| `u`      | 毫秒 |

例如，字符串 `1h30m` 表示在过期时间之前 1 小时 30 分钟。

##### `strategy` {#strategy}

对于数据资源，Angular Service Worker 可以使用以下两种缓存策略之一。

| 缓存策略 | 详情                                                                                                                                                                                                                                                                                                                                                   |
| :----------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `performance`      | 默认策略，针对尽可能快的响应进行优化。如果某个资源存在于缓存中，就使用缓存的版本，不发出网络请求。这会根据 `maxAge` 容许一定程度的数据过时，以换取更好的性能。它适用于不经常变化的资源，例如用户头像图片。 |
| `freshness`        | 针对数据的时效性进行优化，优先从网络获取所请求的数据。只有当网络按照 `timeout` 超时时，请求才会回退到缓存。它适用于频繁变化的资源，例如账户余额。                                                                              |

::: tip 提示
你还可以模拟第三种策略 [staleWhileRevalidate](https://developers.google.com/web/fundamentals/instant-and-offline/offline-cookbook/#stale-while-revalidate)：如果有缓存数据就返回缓存数据，同时在后台从网络获取最新数据供下次使用。
要使用这种策略，请在 `cacheConfig` 中把 `strategy` 设置为 `freshness`，并把 `timeout` 设置为 `0u`。

:::

它的实际效果如下：

1. 先尝试从网络获取。
2. 如果网络请求没有立即完成，也就是在 0&nbsp;ms 超时之后，忽略缓存时长，回退到缓存的值。
3. 网络请求完成后，更新缓存以供将来的请求使用。
4. 如果该资源不在缓存中，则无论如何都会等待网络请求。

##### `cacheOpaqueResponses` {#cacheopaqueresponses}

Angular Service Worker 是否应该缓存不透明响应（opaque response）。

如果未指定，默认值取决于数据组所配置的策略：

| 策略                             | 详情                                                                                                                                                                                                                                                                                                                     |
| :------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 使用 `freshness` 策略的组   | 默认值为 `true`，Service Worker 会缓存不透明响应。这些组每次都会请求数据，只有在离线或网络较慢时才会回退到缓存的响应。因此，Service Worker 是否缓存了错误响应并不重要。                                         |
| 使用 `performance` 策略的组 | 默认值为 `false`，Service Worker 不会缓存不透明响应。这些组会持续返回缓存的响应，直到 `maxAge` 到期，即使错误只是由暂时的网络或服务器问题引起的。因此，如果 Service Worker 缓存了错误响应，就会出问题。 |

::: tip 关于不透明响应的说明
如果你还不熟悉，[不透明响应](https://fetch.spec.whatwg.org#concept-filtered-response-opaque)是一种特殊类型的响应，当请求位于不同源、且该源不返回 CORS 头的资源时，就会返回这种响应。
不透明响应的特点之一是 Service Worker 不能读取它的状态，也就是说，它无法检查请求是否成功。
更多详情，参见 [Introduction to `fetch()`](https://developers.google.com/web/updates/2015/03/introduction-to-fetch#response_types)。

如果你无法实现 CORS —— 例如，你无法控制该源 —— 对于会产生不透明响应的资源，建议使用 `freshness` 策略。
:::

#### `cacheQueryOptions` {#datagroups-cachequeryoptions}

详情参见 [assetGroups](#assetgroups)。

### `navigationUrls` {#navigationurls}

这个可选部分允许你指定一个自定义的 URL 列表，这些 URL 会被重定向到索引文件。

#### 处理导航请求 {#handling-navigation-requests}

ServiceWorker 会把不匹配任何 `asset` 组或 `data` 组的导航请求重定向到指定的[索引文件](#index)。
满足以下条件的请求会被视为导航请求：

- 它的[方法](https://developer.mozilla.org/docs/Web/API/Request/method)是 `GET`
- 它的[模式](https://developer.mozilla.org/docs/Web/API/Request/mode)是 `navigate`
- 根据 `Accept` 头的值判断，它接受 `text/html` 响应
- 它的 URL 符合以下条件：
  - URL 的最后一个路径段中不能包含文件扩展名（即 `.`）
  - URL 中不能包含 `__`

::: tip 提示
要配置导航请求是否发送到网络，请参见 [navigationRequestStrategy](#navigationrequeststrategy) 一节和 [applicationMaxAge](#applicationmaxage) 一节。

:::

#### 匹配导航请求的 URL {#matching-navigation-request-urls}

虽然这些默认条件在大多数情况下都没问题，但有时也需要配置不同的规则。
例如，你可能希望忽略特定的路由，比如那些不属于 Angular 应用的路由，并把它们透传给服务器。

该字段包含一个 URL 和[类 glob](#modifying-the-configuration) URL 模式的数组，它们会在运行时进行匹配。
它既可以包含否定模式（即以 `!` 开头的模式），也可以包含非否定的模式和 URL。

只有 URL 匹配**任意一个**非否定 URL/模式、且**不匹配任何**否定模式的请求，才会被视为导航请求。
匹配时会忽略 URL 查询字符串。

如果省略该字段，则默认为：

```ts
[
  '/**', // 包含所有 URL。
  '!/**/*.*', // 排除指向文件的 URL（最后一段中包含文件扩展名）。
  '!/**/*__*', // 排除最后一段中包含 `__` 的 URL。
  '!/**/*__*/**', // 排除其他任意段中包含 `__` 的 URL。
];
```

### `navigationRequestStrategy` {#navigationrequeststrategy}

这个可选属性允许你配置 Service Worker 如何处理导航请求：

```json
{
  "navigationRequestStrategy": "freshness"
}
```

| 可选值 | 详情                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| :-------------- | :---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `'performance'` | 默认设置。提供指定的[索引文件](#index)，该文件通常已被缓存。                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| `'freshness'`   | 把请求透传到网络，离线时回退到 `performance` 的行为。当服务器使用 `3xx` HTTP 重定向状态码把导航请求重定向到别处时，这个值很有用。使用这个值的原因包括： <ul> <li> 当身份验证不由应用处理时，重定向到身份验证网站 </li> <li> 在网站改版后重定向特定的 URL，以免破坏现有的链接/书签 </li> <li> 当某个页面暂时宕机时，重定向到其他网站，例如服务器状态页 </li> </ul> |

::: warning 重要
`freshness` 策略通常会导致更多请求发送到服务器，这可能会增加响应延迟。建议尽可能使用默认的 performance 策略。

:::

### `applicationMaxAge` {#applicationmaxage}

这个可选属性允许你配置 Service Worker 从缓存中提供某个应用版本的时长。这个时长从你构建应用的时间开始计算，而不是从文件被缓存到设备上的时间开始计算。

在 `applicationMaxAge` 之内，Service Worker 会从缓存中提供文件。超出这个时长后，Service Worker 会把所有请求（包括资源请求和数据请求）都发送到网络，即使并没有更新的版本。在部署新的构建并且设备获取到它之前，应用都无法离线工作。

如果省略 `applicationMaxAge`，则没有最大时长限制，无论缓存的版本有多旧，Service Worker 都会提供它们。
