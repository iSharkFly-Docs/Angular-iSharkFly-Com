# 资源在产生值之前就已完成 {#resource-completed-before-producing-a-value}

当基于 `Observable` 的资源（Resource）——[`rxResource`](/ecosystem/rxjs-interop#using-rxresource-for-async-data) 或 [`httpResource`](https://angular.dev/api/common/http/httpResource)——在既没有发出值、也没有发出错误的情况下就结束（完成）时，就会出现这个错误。

资源最终总要得到 _某种结果_：要么是加载到的值，要么是说明出了什么问题的错误。一个只是悄无声息地完成的 Observable 不会给 Angular 其中任何一样，Angular 不知道该往资源里放什么，于是就抛出这个错误。

## 使用 `httpResource` 时 {#with-httpresource}

`httpResource` 并不需要你自己编写 Observable——它在内部通过 `HttpClient` 发起 HTTP 调用，并在响应返回后完成。所以如果你看到这个错误来自 `httpResource`，问题并不在请求本身，而是位于它前面的某个环节在响应到达之前就把它吞掉了。

最常见的罪魁祸首是某个 `HttpInterceptor` 捕获了错误却没有重新发出任何东西。这与下文的 `EMPTY` 错误是同一个问题，只不过出现在拦截器里，而不是你自己的代码中：

```ts
@Injectable()
class MyInterceptor implements HttpInterceptor {
  intercept(req: HttpRequest<unknown>, next: HttpHandler) {
    return next.handle(req).pipe(
      // 错误示范：与在 `stream` 中使用 `catchError(() => EMPTY)` 是同一个问题——
      // 请求完成时既没有响应也没有错误，
      // 任何依赖它的 httpResource 都会触发 NG0991。
      catchError(() => EMPTY),
    );
  }
}
```

修复方式与一般拦截器管道中的做法相同：让错误继续传播（去掉 `catchError`），或者把它替换成真正能让请求有结果的东西，比如 `of(new HttpResponse({body: fallbackValue}))`。

## 使用 `rxResource` 时 {#with-rxresource}

最容易意外导致这个错误的方式，是捕获错误后用 `EMPTY` 把它吞掉：

```ts
import {rxResource} from '@angular/core/rxjs-interop';
import {EMPTY, catchError} from 'rxjs';

const userResource = rxResource({
  params: () => ({id: userId()}),
  stream: ({params}) =>
    this.http.get(`/users/${params.id}`).pipe(
      // 错误示范：这会把错误完全隐藏起来。Observable 什么都不发出就完成了，
      // 资源既没有值也没有错误可以展示——
      // 正是这种情况触发了 NG0991。
      catchError(() => EMPTY),
    ),
});
```

另一种常见情况是：组合多个 Observable（使用 `merge`、`race` 等），其中某一个可能在发出任何值之前就自行完成，而又没有用 `startWith(...)` 来保证一个初始值。如果所有被组合的源在全部完成之前都没有发出过值，组合后的流也会以空结果完成。

根据你的情况选择合适的修复方式：

**让错误透传出去。** 如果你不需要自己处理错误，直接删掉 `catchError` 即可——资源最终会进入 `error` 状态，你本来就可以用 `userResource.error()` 检查它。

```ts
stream: ({params}) => this.http.get(`/users/${params.id}`),
```

**用回退值恢复。** 如果你更希望显示一些内容而不是错误，可以用 `catchError` 返回一个会发出值的 Observable，比如 `of(...)`：

```ts
import {of, catchError} from 'rxjs';

stream: ({params}) =>
  this.http.get(`/users/${params.id}`).pipe(
    catchError(() => of(null)), // 资源以 `null` 解析，而不是出错
  ),
```

无论哪种方式，都要确保你从 `stream` 返回的 Observable 在完成之前至少发出一个值或一个错误。

## 你实际会在哪里看到这个错误 {#where-you-ll-actually-see-this-error}

这个错误不会在资源创建时抛出，也不一定在请求完成的地方抛出。它会在下一次有代码读取资源的值时抛出——例如模板绑定中的 `userResource.value()`。这可能让 bug 看起来出在应用的其他地方，而真正的原因却在上游（`stream` 以空结果完成，或者某个拦截器吞掉了响应）。

如果你的代码在读取 `.value()` 之前没有检查资源的状态，这个错误可能会一路冒泡到 Angular 的全局 `ErrorHandler`，就像渲染模板时抛出的其他未捕获错误一样。

有两种方式可以降低它的影响，按推荐程度从高到低排列：

1. **从根源上修复**，使用上面介绍的某种方法，让资源永远不会进入这种状态。
2. **对 `.value()` 的读取加以防护**，作为纵深防御，以防某些你无法完全掌控的东西（例如第三方拦截器或服务）意外地以空结果完成。在读取 `.value()` 之前先检查 `.hasValue()` 或 `.status()`，例如使用 `@if (userResource.hasValue()) { {{ userResource.value() }} }`，而不是无条件地读取 `.value()`。
